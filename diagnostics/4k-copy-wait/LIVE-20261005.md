# Unlocked two-window movement and vblank-reference measurements

The running `hdmi-termux-vblank-min-coexist-usb-bt-perf-20261002` bundle was measured again on 2026-10-05. Xorg PID 1144 uses the matched private Mesa `daa6e56de`, O2 diagnostic Xorg/glamor/modesetting, FD740 glamor, TearFree and startup-only DRM tracing at physical 3840x2160@60. No compositor owns `_NET_WM_CM_S0`. USB/Bluetooth forwarding and plane reservation remain as deployed. The user's Firefox PID 2373 remained running.

The tests did not restart the lease, change the output mode, alter the global vblank setting, attach a debugger or use kernel probes. Automation closed only its own windows and processes. Measurements and source snapshots are retained locally in `~/Downloads/hdmi-latency-20261005/`. The compact published data is [live-20261005-summary.json](live-20261005-summary.json); repeatable measurement scripts are in [live-tools](live-tools/).

## One moving window, two moving windows, one again

After the user unlocked xsecurelock, automation created two 900x900 Konsole windows on the right side of the desktop. It moved one, then both, then one again for 18 seconds per phase. The target was 60 batches/s; each batch issued all moves before one XSync. Windows were kept above ordinary windows, actual root coordinates were sampled, and a guard checked that the HDMI desktop remained unlocked. Both windows moved during the middle phase. They were closed and the previous focus restored at the end.

| Measurement | One before | Two | One after |
|---|---:|---:|---:|
| Actual movement batches/s | 45.33 | 42.48 | 45.37 |
| XSync p95 | 25.07 ms | 34.84 ms | 25.27 ms |
| Xorg CPU time over 18 s | 9.06 s | 9.65 s | 9.19 s |
| Mean blocking `glamor.finish` | 5.06 ms | 5.59 ms | 4.92 ms |
| Per-report p95 finish upper bounds | 10.50–13.75 ms | 11.00–14.25 ms | 10.50–12.00 ms |
| Time in blocking finish | 24.68% | 27.76% | 24.15% |
| TearFree damaged-region pixels/s | 40.99 million | 80.79 million | 41.19 million |
| Temporary-copy attempts/s | 45.73 | 85.29 | 45.91 |
| Temporary-copy region pixels/s | 38.29 million | 70.92 million | 38.42 million |

Only complete five-second diagnostic reports entirely inside each phase were selected. The finish and TearFree measurements each cover three reports, about 15 seconds. Independently selected temporary-copy reports cover 10.01, 10.01 and 15.03 seconds respectively. Pixel counts sum rectangle areas; they are not measurements of memory-bus traffic. XSync acknowledges request processing, not repaint completion or physical scanout. Movement batches/s must not be called displayed FPS. Aggregate diagnostics were enabled throughout; their logging overhead has not been established by a disabled/enabled comparison.

Two moving windows nearly doubled damage and temporary-copy activity, while mean finish increased by roughly 10–14% and request-turnaround p95 by about 38%. The return phase closely reproduced the first phase. This supports a substantial synchronization/event-processing cost alongside copying; it does not rule out bandwidth pressure or isolate every source of the turnaround tail. Finish includes earlier outstanding GPU work, not just the final damage copy. No new GBM allocation or TearFree flip failure occurred in these phases. These particular glamor-copy counters reported no upload/readback attempts; they do not cover all transfer paths.

## A bounded reference restores vblank accounting

A separate movement experiment queued one CRTC-sequence event 1200 refreshes ahead on CRTC 235, using a separate DRM FD. The kernel retains a vblank reference until that event completes. It arrived at its exact target, approximately 20 seconds later, and was drained before the FD was closed. This was one bounded event, not periodic polling or a persistent setting change.

| Selected measurement | Before reference | Reference held | After event completed |
|---|---:|---:|---:|
| Selected duration | 20.05 s | 15.02 s | 10.25 s |
| TearFree callbacks | 1156 | 883 | 319 |
| Repeated MSC | 1156 | **0** | 319 |
| Mean callback-minus-UST age | 70665.82 ms | **1.49 ms** | 2978.19 ms |
| Maximum UST age | 80588.24 ms | **7.90 ms** | 10404.38 ms |
| Mean blocking finish | 5.72 ms | 5.42 ms | 5.00 ms |

The live `vblankoffdelay` remained `-1`, and the monotonic DRM timestamp capability was already verified. Acquiring a sustained reference restored fresh MSC/UST values, and the problem returned after its release. This establishes a vblank-reference/accounting problem in the current stack. It does not establish duplicate physical frames, prove a user-visible speedup, or demonstrate that correcting timestamps eliminates the measured GPU wait. Workload/background damage varied in this experiment, especially after the reference completed, so these phases are unsuitable for an interaction-performance improvement percentage.

Installed `msm_drm` reports SCM version `gec2e039129f2`, matching vendor commit `ec2e039129f2b8f93fdfe62a8c6a595efb63d496`; the main kernel matches `d00ba216ccda5d4fcc0d864729ae69d5b63d860c`. Source inspection explains how flip callbacks can arrive with stale accounting:

- The [SDE CRTC implementation](https://github.com/LineageOS/android_kernel_sony_sm8550-modules/blob/ec2e039129f2b8f93fdfe62a8c6a595efb63d496/qcom/opensource/display-drivers/msm/sde/sde_crtc.c) caches and sends page-flip events separately from enabling the DRM vblank callback. Its page-flip implementation is `drm_atomic_helper_page_flip`; the event capture/send path does not acquire/release a vblank reference for that event.
- [SDE commit completion](https://github.com/LineageOS/android_kernel_sony_sm8550-modules/blob/ec2e039129f2b8f93fdfe62a8c6a595efb63d496/qcom/opensource/display-drivers/msm/sde/sde_kms.c) waits for hardware commit completion and then sends the flip event.
- The [legacy page-flip ioctl](https://github.com/LineageOS/android_kernel_sony_sm8550/blob/d00ba216ccda5d4fcc0d864729ae69d5b63d860c/drivers/gpu/drm/drm_plane.c) acquires a reference for `page_flip_target`, which this driver does not expose. The ordinary atomic-helper page-flip route does not acquire it there.
- [DRM vblank accounting](https://github.com/LineageOS/android_kernel_sony_sm8550/blob/d00ba216ccda5d4fcc0d864729ae69d5b63d860c/drivers/gpu/drm/drm_vblank.c) sends the last processed count/time in the event. Negative off-delay disables accounting immediately once references are released. A future queued sequence event explicitly retains a reference until completion.

This source path plus the controlled reference experiment explains the stale event metadata. A production fix needs balanced reference ownership across completion, cancellation and power/modeset transitions, or a carefully scoped Xorg workaround. No kernel or Magisk fix was installed or implemented in this investigation. Do not tune Mesa's target-MSC lead using the stale values.

## Isolated hardware copy costs

An offscreen shader benchmark used the complete deployed Mesa stack, including its private GBM backend. It allocated 4K textures, drew either 900x900, 1400x1000 or full-4K regions, and completed each chain with glFinish. Each configuration had eight warmups followed by 60 samples, with a 60-Hz submission target. Pixel checks passed for all nine configurations. There was no X connection or modeset; the live desktop remained active in the background. GPU-clock snapshots before and after every configuration were 220 MHz, not a continuous frequency trace or a forced clock.

| Region | Linear → linear, mean total | Private texture → linear, mean total | Linear → temporary → linear → destination, mean total |
|---|---:|---:|---:|
| 900x900 | 2.56 ms | 2.19 ms | 3.73 ms |
| 1400x1000 | 3.03 ms | 2.60 ms | 4.79 ms |
| 3840x2160 | 5.79 ms | 5.41 ms | 11.06 ms |

The full-4K total p95 values were 7.51, 6.55 and 12.55 ms. Extra copy legs therefore have a measurable cost. The temporary texture layout was selected by Mesa; it was not independently proven tiled or compressed. This synthetic chain models extra copy work but is not an exact replay of glamor allocation, shaders, overlap handling, rendering or presentation. These timings are CPU wall-clock intervals around submission/completion, not isolated GPU timestamps, and must not be subtracted directly from the desktop results.

A follow-up used 30 native-fence samples per full-4K configuration to separate fence creation/export from the wait:

| Full-4K path | Draw + create/flush/export/destroy, mean | Remaining fence poll, mean | Create-sync mean | FD-export mean |
|---|---:|---:|---:|---:|
| Linear → linear | 1.89 ms | 3.92 ms | 0.68 ms | 0.90 ms |
| Private → linear | 1.85 ms | 3.47 ms | 0.62 ms | 0.89 ms |
| Three-copy chain | 2.69 ms | 8.59 ms | 1.40 ms | 0.67 ms |

The explicit glFlush averaged only 0.027–0.036 ms, but that is not the whole submission cost: native-fence creation already flushes, and export waits for the submission/fence FD to materialize. The deployed source calls `st_context_flush` in `dri_create_fence_fd`; Freedreno's `fence_get_fd` waits for CPU-side batch/submission readiness, while KGSL creates the timestamp fence after submission. This does not imply those operations wait for GPU completion. The still-unsignaled exported fences successfully completed when polled. Thus event-loop completion could free several milliseconds of Xorg processing time, while retaining nonzero synchronous submission/export costs. A real Xorg candidate and lifecycle validation are still required.

## Validation limits and next changes

Initial two-window attempts and the later Maps/reference comparison ran behind an xsecurelock obscurer. Application geometry or `--onlyvisible` did not establish visible scanout. Those comparisons were discarded; only the repeated **unlocked** two-window run above is used for movement conclusions. The earlier bounded-reference test predates the observed lock episode and establishes accounting behaviour; it is not used to claim an interaction speedup.

The first offscreen benchmark attempts omitted `GBM_BACKENDS_PATH`, loaded both system and private Gallium, and crashed their own test process at context creation. They produced no benchmark result and no observed GPU fault. Supplying the complete private backend path resolved the mismatch. The published benchmark now rejects mixed Mesa before creating its context. Xorg itself was verified to map the matched private Mesa backend and Gallium; it was not affected by that test-launch mistake.

The measured engineering priorities are:

1. Correct or work around vblank reference ownership before trusting MSC/UST for bridge scheduling.
2. Replace Xorg's blocking completion wait with fence-driven event-loop readiness, retaining safe synchronous fallback and correct damage, fake-flip and teardown lifetimes. Copy-pending state must be distinct from a submitted kernel flip: existing flip-draining code assumes the latter already has a DRM event.
3. Reduce the confirmed root-overlap temporary-copy work where correctness permits. Investigate tiled/private root designs separately from scanout and fallback paths; this benchmark does not validate such a change.
4. Directly time the client-side Mesa bridge in a matched diagnostic build. Its full-drawable synchronous blit remains a source-level concern, not a separately timed result here. The locked Maps comparison contributes no new usable performance evidence.

Compiler optimization alone cannot remove these copy and completion dependencies. Hardware acceleration and TearFree remain enabled. No asynchronous TearFree candidate, tiled-root change or new restart bundle is claimed ready by this report.
