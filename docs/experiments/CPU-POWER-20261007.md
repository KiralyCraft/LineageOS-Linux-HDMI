# CPU power guard: live 4K30, doze and unplug validation

## Tested runtime

- Device: XQ-DQ72, Lineage 22.2-20250608-NIGHTLY-pdx234, Android API 35.
- Installed CPU module: `0.1.1-d2c8c59df833`; native guard SHA256
  `7bfd78cee46c27af3a3511650cefc58918d5c18fe19920007544f0600b5e37b2`.
- Existing graphics/input module and companion unchanged. Companion build
  `b94d083be9d2129269a61e7c1d001aee44b15c97055abc54435b568e24964924`.
- BCDEF runtime: `hdmi-termux-vblank-min-coexist-usb-bt-bcdef-controls-20261005`,
  continuous leased Xorg, DP-1 at 3840x2160@30. Startup DRM tracing only.
- Android reported `mWakefulness=Dozing` during the screen-off workload.

Private CPU traces sampled policy frequency ceilings/current frequencies and
core_ctl minimum/maximum/active core counts approximately every 200 ms. Raw
traces and vendor binaries are not published. No frequency or thermal sysfs
knobs were written. Native compilation ran on `root@192.168.104.201`.

## Results

Core ranges below are requested hardware core_ctl minimum/maximum counts, not
Linux's online CPU bitmap. The prime cluster contains the one Cortex-X3 core.

| State | Performance ceiling | Performance cores min/max | Prime cores min/max |
|---|---:|---:|---:|
| No lease, phone awake | 2803.2 MHz | 3 / 4 | 0 / 1 |
| No lease, phone off | 940.8 MHz | 2 / 2 | 0 / 0 |
| Active lease, phone awake | 2803.2 MHz | 4 / 4 | 1 / 1 |
| Active lease, phone dozing | 2803.2 MHz | 3 / 4 | 0 / 1 |
| Unplugged while phone off | 940.8 MHz | 2 / 2 | 0 / 0 |
| Subsequent wake | 2803.2 MHz | 3 / 4 | 0 / 1 |
| Subsequent doze | 940.8 MHz | 2 / 2 | 0 / 0 |
| Subsequent wake again | 2803.2 MHz | 3 / 4 | 0 / 1 |

The frequency part worked: the performance cluster reached 2803.2 MHz in both
the awake and dozing workload. Each workload used three independent SHA256
workers for about five seconds, nice level 10, inherited affinity. Android's
wakefulness was checked before and after each workload. These small samples
are not a browser, display-cadence or throughput benchmark.

The core-floor part failed across the phone's OFF transition: minimum cores
dropped from 4/1 to 3/0 although the guard was renewing a positive vendor handle.
The maximums stayed 4/1, so those cores remained available to normal scheduling;
the guard's intended persistent minimums were no longer applied. A finite fresh
overlapping core request returned a positive handle but also left minimums at
3/0. This is consistent with stale cached votes after a hardware-policy reset,
not proof of the precise vendor instruction that reset the nodes.

## Unplug while dozing

The user unplugged while the phone remained off, waited about 15 seconds,
woke it, dozed again, then woke it again. Both the original recorder and a
detached tmux recorder captured the policy transitions.

The broker reported external disconnection at wall time 1791383508.804. The
detached trace last observed the normal ceiling at 1791383508.965570 and first
observed the restored 940800 kHz ceiling at 1791383509.169385. At this sampling
resolution, CPU policy restoration occurred between approximately **162 and
365 ms after the broker's disconnect report**. This is not latency from the
physical cable motion, and not a display presentation measurement.

The performance core limit became two and prime limit zero, with settled
active counts of two and zero. Subsequent wake/doze/wake toggled between the
ordinary Android policies again. Final read-only checks found:

- Broker state `AGENT_READY`; Android owns the display, no active timing.
- CPU lease property `0`; guard-owned core handle `0`, last renewal timestamp `0`.
- Guard's remembered Android state and effective state both awake.
- No leased Xorg process; graphics companion refcount `0`.
- Continuous agent left waiting for another user-armed session.

Both owned CPU recorders were stopped after collecting the result. No Magisk
module was installed, removed or changed by the validation tools.

## Fixes and remaining validation

The initial a90311d package failed closed because Magisk deletes customize.sh
after installation. d2c8c59 corrected runtime checksum coverage and the boot
gate/preload then activated successfully.

The first live boot also exposed a startup retry using uninitialized OFF hint
arguments for ON before any OFF event. A real same-state ON request with type
-1 returned a valid handle. Cycling the phone OFF/ON initialized the installed
version for this test. ab73862 preserves both ON and OFF payloads separately;
its fixture exercises an initial ON failure before the first OFF callback.

cf1bb2c adds core-vote retirement before display-policy submission, followed
by a fresh acquisition. The fixture models a hardware reset with cached votes
retained: the preceding guard fails that case, while the corrected guard passes
under ASan/UBSan. Other lease-loss, invalid-response, timeout, expiry and
installer-cleanup tests also pass.

## Follow-up: installed 0.1.3, core writers and actual CPU placement

The user installed `hdmi-los-cpu-power-cf1bb2c874b7-magisk.zip` and rebooted.
Guard SHA256 was
`5e42f03bef5721d1032b17d957476b347c0216d67e55aa54b52486120fb801fa`.
The boot gate passed and ON policy initialized with type -1 before any OFF
callback, without requiring a manual screen cycle.

The core-vote ordering change did **not** fix the persistent minimums. Active
HDMI while awake again had minimums 4/1; screen-off reset them to 3/0 despite
fresh, positive handles. Maximums remained 4/1 and the performance ceiling
remained 2803200 kHz. Thus the intended forced-floor behavior failed, but the
original panel-off CPU exclusion/cap remained removed.

A targeted open/write trace over only the two core_ctl minimum nodes and the
three candidate vendor services identified PerfHAL's PERFD-SERVER thread as
all their writers during wake/off. It wrote 4/1 after wake and later restored
3/0. Sony poweropt-service did not write those nodes in this interval. The
tracer was detached afterward. Exact private trace timestamps are retained
locally. No service was stopped or restarted.

The installed kalama profile also defines Doze hint 0x1053 using resource
0x42c34000. The PowerHAL source inspected treats DISPLAY_INACTIVE as unsupported.
Neither observation proves where the Doze hint originates or that it caused
the minimum reset. Doze interception is not part of the proposed fix.

### Demand scaling instead of forced idle-core minimums

Two bounded five-second, eight-worker SHA256 tests used nice 10 and inherited
affinity. No `sched_setaffinity`, cpuset writes, frequency changes or thermal
changes were made. Android reported Dozing before and after both tests.

- Scaling sample: performance active count reached 4; prime count reached 1.
  Sampled current frequencies reached 2803200 and 3187200 kHz respectively.
  A frequency read is not proof which workload ran on that CPU.
- Separate placement sample: reading each worker's `/proc/PID/stat` last-CPU
  field at 50 ms intervals observed execution on **all CPUs 0–7**. This includes
  the Cortex-X3. Those samples establish CPU use, not migration latency or
  browser responsiveness.
- Stored allowed masks for the chroot shell, agent and Xorg were 0–7. Root,
  foreground and restricted cpusets all permitted 0–7. Termux:X11's 13 app
  threads also allowed 0–7; its native X server was not running in this capture.
- An idle `sched_getaffinity()` query omitted CPUs 5/7 even for PID 1 while
  `/proc/PID/status` retained 0–7. The subsequent unchanged-affinity workload
  used both CPUs. This was not an inherited six-CPU restriction in the chroot.

These tests demonstrate availability while dozing for the installed 0.1.3.
They do not establish full performance for every workload, absence of wakeup
latency, or standalone Termux:X11 behavior through every app lifecycle state.

### Version 0.1.4 implementation

The revised guard selects the vendor's normal interactive CPU policy while
Android is awake or HDMI is leased, with no separate minimum-core request.
Cores remain available for demand scaling, including the X3, and may idle when
unused. The monitor's disconnect and stale-lease restoration mechanism is
unchanged. Ordinary awake Termux:X11 retains Android's normal policy.

The remote NDK build and host ASan/UBSan lifecycle fixtures passed. The
fixtures reject any direct core/frequency vote and verify forwarding of
separate Doze hints. A standalone Bionic lookup probe on the phone confirmed
interception against only the synthetic client, without contacting PerfHAL.
The new native guard SHA256 is
`ce3c59ff70fd827e5366ae75602135332058fe6fced617424c946639c5d6c935`.

### Installed 0.1.4: awake, dozing and unplug passed

The user installed `hdmi-los-cpu-power-98f97e06dee7-magisk.zip` and rebooted.
ZIP SHA256:
`790b2ae064d84eb700a8536c4a8b1ff34827273a2da023231676c705ea4dda50`.
The latest boot gate passed; the mapped guard matched the SHA above. Before
HDMI connection the lease was zero, with the guard correctly initialized to
Android awake / effective awake. The continuous BCDEF agent was then prepared,
and the user armed and connected the 4K30 output.

Two five-second tests each used eight SHA256 workers, nice 10, unchanged
inherited affinity. Policy/core state and per-worker last-CPU were sampled
every 50 ms. Android's framework state was checked before and after each test.

| Installed 0.1.4 test | Android state before/after | Worker CPUs observed | Performance sampled peak | X3 sampled peak |
|---|---|---|---:|---:|
| HDMI, phone awake | Awake / Awake | 0–7 | 2803.2 MHz | 3187.2 MHz |
| HDMI, phone off | Dozing / Dozing | 0–7 | 2803.2 MHz | 3187.2 MHz |

In both cases the active performance count reached four and prime count one.
Hardware minimums stayed at the normal 3/0; the new guard issued no forced
minimum-core request. Cores idled again after demand subsided. This confirms
that X3 access did not require the discarded minimum-core vote.

The user unplugged HDMI without waking the phone. A subsequent framework check
still reported Dozing. The recorder captured restoration of 940800 kHz and
core maximums 2/0; settled active counts were 2/0. The X3 frequency-policy value
itself remained 3187200 kHz, but its core maximum was zero: the value is not
proof that an unavailable core can execute work.

Final checks confirmed CPU lease zero, no active broker lease, no leased
Xorg, remembered Android state OFF, applied CPU state OFF, and companion
refcount zero. The owned CPU recorder was stopped, and the continuous agent
was left waiting. No new ON event was needed for restoration.

[Aggregated measurements](CPU-POWER-20261007-v014.json) retain workload bounds,
CPU placement sets, sampled peaks and the policy transition. Raw 50/200 ms
traces remain private. The physical cable-disconnection instant was not
measured, so no precise unplug-latency claim is made for this version.

This completes the installed version's awake → Doze → unplug-while-dozing
acceptance sequence. Standalone Termux:X11 GUI workloads, repeated reconnects,
service-crash recovery, suspend/resume and thermal stress remain separate
checks. No Maps or physical display-cadence improvement is claimed.
